# P12

## Goal
实现 LLM 适配层与 provider-native reasoning stream 落盘；生产模式只取结构化决策，不要求 pass/fail reasons；对不支持 reasoning stream 的模型不报错。

## Status
`PASSED`

## Actual Changes
- 新增 `src/llm-adapter.js`：
  - `buildScreeningLlmRequest`
  - `runStructuredScreening`
- 支持两类生产 decision contract：
  - Recommend: `{ decision: "pass" | "fail", post_action: "chat" | "none" }`
  - Chat: `{ decision: "pass" | "fail", post_action: "request_resume" | "none" }`
- LLM request 只包含：
  - required decision fields
  - screen input manifest
  - candidate info
  - CV payload
- provider 可通过 `onReasoningDelta` 传入原生 reasoning/CoT chunk。
- 只有 provider 实际发送 reasoning chunk 时才写 `reasoning.log`。
- provider 不发送 reasoning stream 时正常返回 decision，不创建 reasoning log，也不报错。
- 新增 OpenAI-compatible `/chat/completions` 非流式 JSON 调用骨架。
- 新增 `src/llm-adapter.test.js`。

## Live Validation Evidence
- P12 是本地适配层阶段，不需要网页交互。
- 使用 fake provider 验证：
  - 有 reasoning chunk 时原样写入 `reasoning.log`。
  - 无 reasoning chunk 时 decision 正常返回且不生成 `reasoning.log`。
  - request JSON 不包含 `reason` 字段。

## Learnings
- “不要求理由”应通过 response contract 固定：只允许 `decision` 和 `post_action`。
- reasoning/CoT 只能作为 provider-native side channel 写入，不能通过 prompt 要求模型生成。
- 无 reasoning stream 是正常路径，不能被当成 provider bug。

## Pitfalls
- 不要在后续 prompt 中加入 `reason`、`explanation`、`why` 等输出字段。
- `reasoning.log` 是否存在不能作为 run 成功条件；decision JSON 才是生产必要产物。
- 当前默认 HTTP 调用是非流式 JSON；真实 provider 的 streaming 事件解析可在接入具体 provider 时补，但必须保持同样的 `onReasoningDelta` 抽象。
