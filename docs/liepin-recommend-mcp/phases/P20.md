## Learnings
- P20 可以复用 P19 的同 modal `下一位` 模式处理 20 位候选人；实机 20 位全部得到唯一 `textHash`。
- 使用 `--step-delay-ms 5500` 后，20 位详情读取没有触发 risk/captcha。
- 推荐页 modal snapshot 直接走 P09 parser 和 P11 payload audit；本次 20 位全部 `missingParsedSectionIds=[]` 且未截断。
- Mock LLM 返回 `pass/chat` 时，dry-run 仍然保持 `actionClicks=0` 与 `actionExecuted=false`，证明 P20 不会误点推荐动作。
- P20 的 structured request 仍只要求 `{ decision, post_action }`，没有要求 pass/fail reason。
- `candidateLabel` 必须从原始 `innerText` 的首个非空行提取；如果先 normalize 掉换行再 split，会把整份简历重复放入 candidate label。
- 当前 P20 输出会包含完整 `llmRequest` 和 `cv_payload`，证据文件仍较大；后续正式 run artifact 可以改为按 run 目录拆分 `screen-input.json`、`llm-request.json`、`decision.json`、`coverage.json`。

## Pitfalls
- 不要用 P20 结果作为实际沟通依据；P20 是 dry-run，故意不执行动作。
- 如果没有真实 `screening-config.json`，必须显式传 `--mock-llm`；否则命令会要求补配置。
- 20 位连续读取仍属于高频详情访问；继续保持较长 step delay，并在实机前后跑 `research discover`。
- P20 的 evidence 用 mock provider，验证的是 wiring、coverage 与 dry-run 安全性；真实 provider 的质量和 reasoning stream 仍依赖 P12 adapter 与后续实际配置。
