## Learnings
- The old async run shell was structurally sound, but worker routing still pointed at early research sampling. P23 now carries an explicit `workflow` in run input so old and new behavior can coexist.
- `screening-config.json` is still intentionally missing in the live environment. Doctor should treat this as actionable setup guidance, not a code failure.
- `doctor --fix` must be conservative: create missing templates and runtime dirs, but never overwrite user configuration.
- Async `recommend-chat` can still create real greeting side effects if run with P22 chain. Keep `request_resume` dry-run by default and require explicit `execute_request_resume` / `--execute-request-resume` for real resume requests.

## Pitfalls
- Do not resume completed/failed/canceled runs; create a new run instead.
- Do not run `doctor --fix` casually in a user's real home if they have not asked for file creation; the tested behavior is conservative, but it still writes a config template when missing.
- Do not treat doctor `ok=false` as always blocking: missing chat page only blocks chat-only workflows, while recommend-only dry-runs can still proceed.
- P23 async start commands can trigger live DOM interaction. Use `--mock-llm` and small candidate limits for safe validation.

## Next Phase Notes
- Next phase can focus on production gating and operator UX:
  - clearer persisted artifacts for screen input / LLM request / decisions per candidate
  - richer `runs status` summaries without huge payloads
  - explicit approval gates for real `chat` and `request_resume` side effects
  - optional real-provider end-to-end run once `screening-config.json` is available
